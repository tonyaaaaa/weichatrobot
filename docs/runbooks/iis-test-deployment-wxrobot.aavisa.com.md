# wxrobot.aavisa.com IIS Test Deployment

## Topology

```text
https://wxrobot.aavisa.com/
  -> IIS site WechatRobot-Frontend
     -> Vue static files
     -> /api/* ARR rewrite to http://127.0.0.1:5268/api/*

http://127.0.0.1:5268/
  -> IIS site WechatRobot-Api
     -> ASP.NET Core Module
     -> WechatRobot.Api

Windows startup task WechatRobot-Worker
  -> dotnet WechatRobot.Worker.dll
```

Only TCP 80 and 443 are public. Port 5268 is bound to loopback. MySQL and Qdrant
must allow only the deployment server's IP.

## Required Windows Components

- IIS with Static Content, HTTP Errors, HTTP Logging, Request Filtering, and WebSocket Protocol.
- IIS URL Rewrite.
- IIS Application Request Routing with server-level proxy enabled.
- .NET 10 Hosting Bundle.
- A valid TLS certificate whose subject includes `wxrobot.aavisa.com`.

After installing the Hosting Bundle, restart IIS:

```powershell
iisreset
```

## Release Layout

Copy the verified release into:

```text
C:\WechatRobot\
  frontend\
  api\
  worker\
  logs\
```

The frontend package already contains `web.config`. The API package contains the
ASP.NET Core Module `web.config` generated by `dotnet publish`.

## IIS Sites

Create application pools:

```powershell
Import-Module WebAdministration

New-WebAppPool -Name "WechatRobot-Frontend"
Set-ItemProperty "IIS:\AppPools\WechatRobot-Frontend" -Name managedRuntimeVersion -Value ""
Set-ItemProperty "IIS:\AppPools\WechatRobot-Frontend" -Name startMode -Value AlwaysRunning

New-WebAppPool -Name "WechatRobot-Api"
Set-ItemProperty "IIS:\AppPools\WechatRobot-Api" -Name managedRuntimeVersion -Value ""
Set-ItemProperty "IIS:\AppPools\WechatRobot-Api" -Name startMode -Value AlwaysRunning
```

Create sites after confirming the physical directories:

```powershell
New-Website -Name "WechatRobot-Frontend" `
  -PhysicalPath "C:\WechatRobot\frontend" `
  -ApplicationPool "WechatRobot-Frontend" `
  -Port 80 `
  -HostHeader "wxrobot.aavisa.com"

New-Website -Name "WechatRobot-Api" `
  -PhysicalPath "C:\WechatRobot\api" `
  -ApplicationPool "WechatRobot-Api" `
  -IPAddress "127.0.0.1" `
  -Port 5268
```

Bind the public certificate to `WechatRobot-Frontend` on port 443 through IIS
Manager or the server's certificate automation. Do not bind the API site publicly.

Enable ARR proxy at the IIS server level:

```powershell
& "$env:windir\system32\inetsrv\appcmd.exe" `
  set config -section:system.webServer/proxy /enabled:"True" /commit:apphost
```

## Machine Environment

Set secrets as machine environment variables, not in `appsettings.json` or
`web.config`. Values below are names only; obtain the real values through the
server's secure administration channel.

```text
ASPNETCORE_ENVIRONMENT=Production
ConnectionStrings__WechatRobot
WECHATROBOT_MASTER_KEY_BASE64
Jwt__Issuer
Jwt__Audience
Jwt__SigningKey
Cors__AllowedOrigins__0=https://wxrobot.aavisa.com
Qdrant__BaseUrl
Qdrant__ApiKey
Oss__AccessKeyId
Oss__AccessKeySecret
Oss__Bucket
Oss__Endpoint
Oss__PublicBaseUrl
Oss__PublicReadRiskAccepted=true
ALIBABA_CLOUD_OCR_ACCESS_KEY_ID
ALIBABA_CLOUD_OCR_ACCESS_KEY_SECRET
BootstrapAdmin__Email
BootstrapAdmin__Password
BootstrapAdmin__DisplayName
Database__ApplyMigrationsOnStartup=true
```

The API and Worker read the same connection string, master key, Qdrant, OCR, and
OSS values. After the first successful start has applied migrations and created
the bootstrap administrator, set `Database__ApplyMigrationsOnStartup=false` and
remove `BootstrapAdmin__Password` from the machine environment.

Keep `WECHATROBOT_MASTER_KEY_BASE64` permanently stable and back it up through
the server's secret-management process. Replacing it makes previously encrypted
robot identifiers and model credentials unreadable. Use a rotated Qdrant API key
that has not been shared through chat or committed to source control.

Use `Oss__AccessKeyId` and `Oss__AccessKeySecret` as the actual machine
environment names. Do not put either value in source-controlled JSON.

## Worker Startup Task

Run the Worker as Local System at machine startup:

```powershell
$dotnet = Join-Path $env:ProgramFiles "dotnet\dotnet.exe"
$worker = "C:\WechatRobot\worker\WechatRobot.Worker.dll"
$action = New-ScheduledTaskAction `
  -Execute $dotnet `
  -Argument "`"$worker`"" `
  -WorkingDirectory "C:\WechatRobot\worker"
$trigger = New-ScheduledTaskTrigger -AtStartup
$settings = New-ScheduledTaskSettingsSet `
  -ExecutionTimeLimit ([TimeSpan]::Zero) `
  -RestartCount 10 `
  -RestartInterval (New-TimeSpan -Minutes 1) `
  -StartWhenAvailable

Register-ScheduledTask `
  -TaskName "WechatRobot-Worker" `
  -Action $action `
  -Trigger $trigger `
  -Settings $settings `
  -User "SYSTEM" `
  -RunLevel Highest `
  -Force

Start-ScheduledTask -TaskName "WechatRobot-Worker"
```

On the first deployment, start the API site and confirm that its database
migrations complete before starting this Worker task. The Worker must not race
the initial schema creation.

## Acceptance Checks

From the server:

```powershell
Invoke-WebRequest http://127.0.0.1:5268/health/live
Invoke-WebRequest -UseBasicParsing https://wxrobot.aavisa.com/
```

From an external machine:

```powershell
curl.exe -I https://wxrobot.aavisa.com/
curl.exe -i https://wxrobot.aavisa.com/health/live
```

The public frontend rule proxies `/api/*` and the non-sensitive liveness endpoint
`/health/live`. Authenticated readiness is checked after login at:

```text
https://wxrobot.aavisa.com/api/admin/health/ready
```

Finally configure both WorkTool callback types with public base URL:

```text
https://wxrobot.aavisa.com
```

Do not record callback success until WorkTool returns acceptance and a real test
message produces a correlated callback in the application audit.
