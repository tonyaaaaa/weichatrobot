# 私聊与群聊全链路延迟和输出安全优化设计

## 背景与生产证据

2026-07-31 的 API、Worker 日志和生产库只读审计显示：

- 最近六小时群聊回复平均约 52.4 秒，P95 约 82.7 秒，最大约 123.6 秒。
- 私聊回复平均约 38.4 秒，P95 约 82.9 秒，最大约 84.5 秒。
- 聊天模型请求平均约 13.36 秒，最长约 20.77 秒；Embedding 平均约
  298 毫秒，Qdrant 平均约 17 毫秒，数据库命令平均约 3.6 毫秒。
- 群聊意图 Agent 平均约 13.9 秒，查询改写 Agent 平均约 12.8 秒，二者
  当前串行执行；私聊查询改写平均约 13.9 秒。
- Worker 只有一个消息消费循环，群聊、私聊和私聊知识入库互相阻塞。
- 默认聊天模型为 `glm-5.2`。供应商文档说明该模型默认开启思考模式，简单
  分类和工具调用可通过 `thinking.type=disabled` 关闭思考以降低延迟。
- 每次回答分别为记忆和知识 RAG 生成同一问题的 Embedding，产生重复网络调用。
- 记忆结果按 GUID 集合查询时在真实 MySQL 提供程序上出现稳定的 EF
  `NullReferenceException`，记忆召回被静默降级。
- 联网搜索响应可能把 ``<|tool_call|>``、`web_search` 参数等内部工具调用
  标记写入正文；现有无证据输出防火墙未识别该格式，导致内部调用被发送给用户。

## 目标

- 同时优化私聊和群聊从回调入库、任务租约、Agent、RAG、记忆、生成到发送的
  完整链路。
- 保留 Agent Framework、多轮查询改写、固定回复和现有上下文配置语义。
- 不修改现有 appsettings 业务配置，不新增数据库迁移。
- 群聊、私聊和知识入库不再因单一串行消费者互相发生队头阻塞。
- GLM 路由/回答请求使用非思考模式，并限制工具型 Agent 的最大输出。
- 无正式上下文的首轮问题直接使用原问题检索，不调用查询改写 Agent；有上下文
  的第二轮仍必须经过 Agent 完整意图改写。
- 同一请求内相同模型、相同文本的 Embedding 只生成一次，供记忆和 RAG 复用。
- 修复真实 MySQL 记忆 GUID 批量查询。
- 任何模型出口都不得把内部工具调用、提示词边界或工具参数发送给用户。
- 新增结构化阶段耗时日志，后续能够直接区分排队、处理和发送耗时。

## 方案

### 1. 按作业类型拆分并发通道

`DurableJobWorker` 的托管执行改为独立通道：

- 群聊 `ProcessInboundMessage`：四个消费者，以现有会话租约保证同一会话顺序。
- 私聊 `ProcessPrivateMessage`：一个独立消费者，保持当前私聊全局串行安全边界，
  但不再被群聊和入库任务阻塞。
- 私聊入库 `ProcessPrivateKnowledgeIngest`：一个独立消费者，不再阻塞回复链。

测试直接调用的 `ProcessOnceAsync` 保持兼容。每个租约返回作业创建时间，Worker
记录 `queueAgeMs` 和 `processingMs`，不记录消息正文或凭据。

### 2. 关闭简单 Agent 的默认深度思考

对智谱官方 GLM 思考模型请求，在 HTTP JSON 顶层注入
`thinking={"type":"disabled"}` 并设置 `max_tokens=2048`。该行为由模型和官方端点识别限定，不影响其他 OpenAI
兼容供应商。Agent Framework 和旧 Chat Completion 两条发送路径使用同一规则。

工具型 Agent 同时设置较小的 `MaxOutputTokens`：意图、固定模板和查询改写只需
返回一个工具调用，不允许生成长文本。RAG 答案保留足够的正文输出上限。

### 3. 删除不必要的模型与 Embedding 调用

- 当正式上下文没有消息且没有摘要时，`MultiTurnRetrievalService` 直接返回经过
  长度限制的原问题，审计标记为 `standalone_fast_path`，Agent 调用次数为零。
- 只要存在历史消息或摘要，仍执行查询改写 Agent；诸如“需要什么材料”“米兰”
  等上下文依赖或歧义问题不会走快速路径。
- 新增请求作用域 Embedding 缓存，以供应商地址、模型和输入文本为键。记忆召回
  与知识 RAG 配置一致时复用向量；配置不同时仍分别调用。

### 4. 修复记忆查询

把 `ids.Contains(entry.Id)` 更换为仓库既有 `GuidBatchQuery` 谓词，避免真实
MySQL 提供程序在 GUID 集合参数化时崩溃。补充真实 MySQL 回归测试，证明召回
能够读取活动记忆而不是返回 `memory_recall_unavailable`。

### 5. 输出安全

`AnswerOutputFirewall` 增加内部工具协议标记检测，至少覆盖：

- `<|tool_call|>`、`<|tool_response|>` 及大小写/空白变体。
- `tool_calls`、`function_call`、工具参数 JSON。
- 包含内部搜索调用的 Markdown 代码块。

RAG、有来源联网搜索、模型知识兜底和查询改写澄清都必须使用统一内部标记检查。
联网搜索正文不安全时不得拼接来源后发送，继续现有安全兜底；所有兜底仍不安全时
返回固定安全失败文案。固定回复和系统静态文案不经过模型，不改变其业务语义。

## 安全与兼容边界

- 不降低回调鉴权、授权、幂等、会话顺序、机器人发送协调或速率限制。
- 不并发处理私聊会话，直到另有正式的私聊会话租约设计。
- 不缓存跨请求 Embedding，不引入陈旧或跨用户数据共享。
- 不记录问题、回答、提示词、API Key、连接串或回调标识。
- 不以字符串规则替代有上下文的 Agent 查询改写。
- 不修改群配置的上下文范围、历史轮数、摘要或机器人历史设置。

## 验收标准

- 单元测试证明首轮无上下文时查询改写 Agent 零调用，有上下文第二轮仍调用一次。
- 单元/集成测试证明三类作业使用独立通道，群聊支持并行且测试入口兼容。
- 请求序列化测试证明智谱官方 `glm-5.2` 包含 `thinking.type=disabled`，非目标供应商
  不被注入。
- 同一请求的记忆与 RAG 相同 Embedding 只触发一次外部调用。
- 真实 MySQL 记忆召回测试通过，不再产生该 EF 查询异常。
- 用户提供的完整 `<|tool_call|> web_search` 样例被防火墙拒绝，且正常中文答案通过。
- 相关后端完整测试、Release 构建和差异检查通过。
- 使用 `.local` 启动后，以相同模型验证私聊、群聊首轮和群聊/私聊第二轮；记录
  优化后 Agent、Embedding、排队和端到端耗时，与本设计中的生产基线比较。
