# 固定回复模板 MySQL Guid 批量查询修复设计

## 背景

生产环境请求 `GET /api/admin/fixed-reply-templates` 时，模板主表分页查询成功，随后 `FixedReplyTemplateStore.ViewsAsync` 加载模板示例时抛出 `NullReferenceException`。异常发生在 `MySql.EntityFrameworkCore` 创建数据库命令期间，触发查询使用了运行时 `Guid[]` 的 `Contains` 表达式。

同一存储类中共有四处相同查询方式，分别服务于后台模板详情组装、群聊固定回复候选和私聊固定回复候选。如果只修复当前列表页，机器人运行时仍可能遇到相同 Provider 异常。

## 目标

- 修复后台固定回复模板列表加载失败。
- 同时修复群聊和私聊固定回复候选加载中的同类风险。
- 保持 API、数据库结构、固定回复匹配规则及返回顺序不变。
- 不执行数据库迁移，不修改正式数据。

## 方案

将 `FixedReplyTemplateStore` 中四处运行时 Guid 集合 `Contains` 查询替换为仓库现有的 `GuidBatchQuery` 模式：

1. 使用 `GuidBatchQuery.CreateBatches` 将模板 ID 限制在固定批次内。
2. 使用 `GuidBatchQuery.BuildPredicate` 生成显式 Guid 等值谓词。
3. 每批执行原有排序查询，将结果合并后继续按现有内存映射逻辑组装返回值。
4. 空模板集合直接返回空子项，不发送无意义查询。

该方案沿用知识库管理查询和物理删除恢复任务已经采用的 MySQL 兼容写法，不增加新的数据访问抽象。

## 数据流

- 后台列表：查询模板页 -> 分批加载示例 -> 分批加载群规则 -> 组装模板视图。
- 群聊匹配：查询有效模板 -> 分批加载示例 -> 保持每模板示例数量限制 -> 返回候选。
- 私聊匹配：查询有效模板 -> 分批加载示例 -> 保持每模板示例数量限制 -> 返回候选。

## 错误处理与并发

本次只替换读取查询的表达式形态，不改变异常边界、写入事务或并发令牌。每个调用已有候选数量上限；分批查询进一步限制单条 SQL 的 Guid 条件数量。

## 测试与验收

- 先增加回归测试，使固定回复读取在不支持运行时 Guid 集合参数的 Provider 行为下失败。
- 修复后验证后台视图组装、群聊候选和私聊候选均能读取示例及群规则。
- 运行固定回复相关集成测试、完整后端单元测试、API 编译和前端构建。
- 不使用容器，不连接或修改正式数据库，不启动 API 或 Worker。

## 发布影响

代码变更位于 Infrastructure，生产环境需要重新发布 API 和 Worker，以保证后台管理与机器人运行路径使用同一修复版本。数据库无需迁移。
