# 管理后台页面完整性与群详情完整实现设计

## 1. 背景

当前管理后台已经具备较多真实 API 和业务能力，但部分页面只完成了路由、
标题、基础表单或跳转入口。自动化测试主要验证接口调用和 DOM 结构，没有覆盖
登录后的视觉完整性，导致“测试通过”与“页面达到已批准预览稿”之间存在差距。

本设计采用已批准的方案 A：

1. 先完整实现单群详情页，不再保留只有四个标签页的骨架版本。
2. 盘点所有后台页面，将问题分为功能缺失、契约缺失和视觉一致性缺失。
3. 已有真实后端能力的页面直接补齐前端工作流。
4. 没有后端契约的能力不得用静态数字、假列表或无效按钮伪装完成。
5. 页面实现、组件测试和登录后浏览器视觉验收必须作为同一交付项。

本设计不改变已经批准的 WorkTool 能力边界，不恢复人工转接，也不使用成员昵称
冒充稳定企业微信身份。

### 1.1 复用优先补充决策

后续确认要求以当前已经存在的真实功能为基础，能够不重新设计就不重新设计。
因此，第 4 节的全站巡检只用于发现真实骨架、缺失状态、控件溢出或无法完成的
操作，不再把“原生控件存在”或“视觉不够新”单独视为重构理由。

- 已有功能闭环且没有可复现缺陷的页面保持不动。
- 群远程操作、用户与角色、机器人设置、知识分段和审计页面先验证现有流程；
  只有测试或浏览器证据证明存在问题时才做局部修复。
- 不为统一外观而批量替换表单、弹框或筛选栏。
- 群详情继续按已批准预览补齐，因为当前实现已经确认缺少真实数据和核心信息
  层级，不属于单纯换皮。

## 2. 页面完整性的统一标准

一个后台页面只有同时满足以下条件才算完成：

- 页面标题、副标题和主要操作能让管理员理解“这里能做什么”。
- 页面展示来自真实 API 或明确的本地草稿，不展示虚构统计和成功状态。
- 核心操作能够在页面内闭环，不能只留下没有解释的跳转链接。
- 异步数据具有加载、成功、空数据、失败和重试状态。
- 表单字段有可见标签、说明、范围限制和就近错误提示。
- 保存、删除、重试等操作有明确的处理中和完成反馈。
- 危险操作使用 `ElMessageBox` 二次确认；普通结果使用 `ElMessage`。
- 页面使用 Element Plus 或现有共享组件，不混用未经设计的原生按钮、输入框和
  自制弹框。文件选择等浏览器能力可以保留原生控件，但必须由一致的外层组件
  承载。
- 键盘可以到达所有操作，焦点样式可见，错误使用 `role="alert"` 或
  `aria-live` 通知。
- 在 375、768、1024 和 1440 像素宽度下无横向溢出；窄屏按业务顺序变为单栏。
- 测试必须验证用户可见行为，不能只断言组件名称或静态文本存在。
- 登录后浏览器验收必须覆盖首次加载、空态、数据态、编辑态、失败态和窄屏。

现有颜色、字体和全局设计变量继续作为系统视觉来源。本轮不引入新的紫色主题、
外部字体或动画框架，避免形成第二套设计系统。界面保持紧凑型运营后台密度，
动效仅用于状态切换和折叠，且遵循 `prefers-reduced-motion`。

## 3. 单群详情完整实现

### 3.1 数据契约

`GET /api/groups/{id}/configuration` 在现有配置上增加两个只读区块。

默认聊天模型能力：

- 是否存在已启用的默认聊天模型。
- 模型配置名称。
- 连接测试状态。
- Web Search 模式。
- 当前是否能够执行 Web Search。
- 不可用时的稳定原因：未配置、未启用、连接未通过或模型不支持。

群级记忆摘要：

- 本群有效群级长期记忆数量。
- 本群有效成员作用域长期记忆总数。
- 本群待整理候选数量。
- 本群正在处理或等待处理的记忆任务数量。

成员作用域数量是本群所有观察到昵称作用域的汇总，不能描述为稳定用户数量。
接口只返回数量，不返回记忆正文、昵称清单、模型输入或凭据。

两组数据与群配置一起加载，保证页面首次渲染只有一个权威快照。统计查询必须在
数据库端完成，不能加载整表后在内存计数。

### 3.2 页面结构

页头只保留一组标题和返回操作，展示：

- 群名称。
- 机器人名称。
- WorkTool 群备注。
- 登记来源。
- 当前生命周期状态。

页面保持四个一级标签：

1. `知识与回答`
2. `上下文与记忆`
3. `运行记录`
4. `高级设置`

四个标签拆分为独立组件。父页面只负责加载、共享草稿、并发版本、未保存离开
保护和统一保存，不再承载所有字段模板。

### 3.3 知识与回答

该标签分为三个连续步骤，使管理员一眼看懂回答链：

1. `先查知识库`
2. `未命中时继续尝试`
3. `仍无可靠答案时`

知识标签使用可搜索多选控件：

- 已绑定标签清晰显示。
- 全局公开标签以只读说明展示，不要求重复选择。
- 已禁用但仍绑定的标签可移除，移除后不可重新添加。
- 无标签时提供进入知识标签页面的真实入口。

回答降级使用流程卡而不是平铺复选框：

- Web Search 开关。
- 模型自身知识开关。
- 网页来源展示开关。
- 结果数量、时间范围、域名和摘要长度采用渐进展示。
- 最终失败策略始终可见。

模型能力区展示真实默认模型状态。启用 Web Search 但模型不支持时，页面显示
“将跳过联网搜索并继续执行后续降级”的明确提示，不阻止保存，也不声称搜索
可用。

### 3.4 上下文与记忆

短期上下文使用 Element Plus 表单，按两组展示：

- 会话边界：群共享或按观察到的成员昵称隔离、空闲超时。
- 输入控制：历史轮数、Token 上限、摘要、机器人历史。

每个继承字段同时显示系统有效值，避免管理员无法判断留空后的行为。

长期记忆使用四张只读摘要卡展示真实数量，并提供：

- `查看当前对话上下文`
- `打开本群记忆中心`

危险区单独展示“清空短期上下文”，明确说明不会删除历史消息、审计和长期
记忆。清空操作不得提交或覆盖尚未保存的普通配置草稿。

### 3.5 运行记录

当前后端没有统一群运营统计 API，因此本标签不展示虚构数量。使用四张带说明和
状态语义的入口卡：

- 当前对话上下文。
- 会话审计。
- 记忆中心。
- 发送队列。

卡片必须说明目标页面会按当前群自动筛选。发送队列继续使用群名称筛选，因为
现有发送命令合同没有稳定群配置 ID；页面应明确这是名称筛选。

### 3.6 高级设置

匹配规则和保存前预览使用两个 `ElCollapse` 项，默认收起。

WorkTool 导入群显示：

> 当前群已通过 WorkTool 准确登记，无需配置匹配规则。

只有管理员主动展开时才显示规则编辑器。规则编辑器统一使用 Element Plus
输入、选择、开关和按钮。正则表达式继续由后端执行超时保护。

### 3.7 保存与错误恢复

- 四个标签共享一份草稿。
- 只有实际修改后才显示固定保存栏。
- 保存时发送完整草稿和 `expectedConfigurationVersion`。
- `409` 时重新加载权威配置并提示复核，不自动重试旧草稿。
- 普通失败保留草稿。
- 标签切换不得丢失内容。
- 路由离开使用 `ElMessageBox`；浏览器关闭仍使用标准
  `beforeunload` 保护。

## 4. 全站页面完整性巡检

### 4.1 P0：存在明显骨架或核心流程难以理解

#### 系统设置

当前页面只有“后端暂未提供系统设置读写 API”的提示。因为缺少真实契约，本轮
不得制作配置表单。页面保留为明确的能力边界，同时输出单独的后端设置服务/API
实施项。只有真实 API、并发版本、审计和运行时读取全部完成后，页面才能改为
可编辑状态。

#### 群远程操作

现有登记、已登记群选择、预览、两分钟确认令牌、执行和结果状态已经形成真实
闭环。本轮先保留现有页面结构，只验证不同操作的字段、令牌失效、错误恢复和
窄屏可用性。只有出现可复现的操作阻塞或布局溢出时才做局部修复，不再整体改成
新的步骤式页面。

#### 群详情

按第 3 节完整实施，是本轮最高优先级。

### 4.2 P1：功能闭环但视觉和交互仍是旧骨架

以下页面保留接口和业务行为，先进行功能与浏览器复核：

- 登录。
- 用户与角色。
- 机器人设置。
- 文档分段详情。
- 知识标签。
- 发送队列、会话审计和管理审计。

只有发现缺少加载/空态/失败恢复、操作无法完成、弹框或输入框溢出、窄屏无法
使用等具体缺陷时，才增加回归测试并进行最小修改。不得仅为统一组件而重写页面，
也不得改变 API 请求、并发版本、权限或业务状态机。

### 4.3 P2：已经完整，主要做一致性复核

- 工作台。
- 群列表。
- 当前对话上下文。
- 文档列表与文档管理。
- 知识学习审核。
- 记忆中心。
- 模型配置。

P2 页面只修复巡检发现的具体问题，例如缺少错误恢复、窄屏溢出、标签不清晰或
原生控件混用；不做无关重构。

## 5. 共享组件与边界

优先建立并复用以下小型组件：

- 页面标题与操作区。
- 加载/失败/空数据状态容器。
- 群选择器。
- 筛选栏。
- 状态标签映射。
- 危险操作区。

共享组件只统一表现和交互，不拥有业务 API，不在内部隐藏权限判断或版本并发
逻辑。业务页面继续负责数据加载和业务动作。

不引入新的表单库。当前字段规模可以使用 Element Plus 的 `ElForm` 和现有
校验方式完成；增加另一套表单依赖会扩大迁移范围。

## 6. 测试与验收

### 6.1 后端

- 群配置合同测试覆盖默认模型能力的所有稳定原因。
- 集成测试覆盖四类记忆统计，并证明统计受群 ID 和有效状态约束。
- MySQL 集成测试覆盖统计查询，不使用仅 SQLite 可运行的表达式。
- 响应不得包含模型密钥、记忆正文或 WorkTool 标识。

### 6.2 前端

- 群详情四个面板分别使用组件测试。
- 测试回答流程的条件展示、模型不支持提示和真实记忆摘要。
- 测试标签切换保留草稿、脏状态保存、409 重载和清空上下文独立性。
- 群远程操作测试不同操作只显示所需字段。
- 被整改页面测试加载、空态、失败、重试和主要操作。
- 全局扫描禁止新增原生 `alert`、`confirm` 和 `prompt`。

### 6.3 浏览器视觉验收

使用真实开发 API 和具有相应角色的测试账号验收，不通过修改鉴权逻辑绕过登录。
逐页保存桌面和窄屏截图，至少检查：

- 1440 像素桌面数据态。
- 768 像素平板布局。
- 375 像素窄屏无横向滚动。
- 加载、空态、失败和编辑状态。
- 键盘焦点顺序。
- 弹框尺寸、遮罩、按钮和输入框不溢出。

无法取得真实数据的状态使用测试数据库构造，不在生产代码中增加演示数据。

## 7. 实施顺序

1. 群配置响应增加默认模型能力与记忆摘要。
2. 群详情拆分四个业务面板并完整还原预览稿。
3. 统一群详情使用的上下文和规则组件。
4. 验证群远程操作现有闭环，只修复有证据的问题。
5. 验证 P1 页面现有功能，只修复有证据的问题。
6. 巡检 P2 页面并保持无缺陷页面不变。
7. 执行前后端全量测试、生产构建和登录后视觉验收。

每一阶段都必须先增加能够失败的回归测试，再编写产品代码。任何页面如果缺少
真实后端契约，必须在实施记录中标记为阻塞，不得用前端假数据跨过边界。
