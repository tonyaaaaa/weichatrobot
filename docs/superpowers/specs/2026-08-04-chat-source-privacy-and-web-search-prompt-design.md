# 聊天来源隐藏与 Web Search 提示修复设计

## 1. 背景与已确认问题

正式环境在私聊收到 `你好` 后，返回了对英文单词 `participant` 的解释，并在
微信消息末尾附加网页来源。正式会话审计证明：

- 入站问题、RAG 检索词均为 `你好`；
- 本轮没有使用历史上下文，不存在用户消息串线；
- 知识库证据不足后进入了模型原生 Web Search；
- Web Search 最终回答错误地围绕 `participant` 展开；
- 私聊回答配置把 `WebSearchShowSources` 硬编码为 `true`，因此来源被追加到
  微信消息。

当前 Web Search 提示把问题包装为 `participant: ...` 与 `content: ...`。GLM
原生搜索工具可能从这段结构化文本中选取前置英文标签作为查询主题，因此把
`participant` 当成了检索词。

用户确认最终产品规则：私聊和群聊的微信回复都不展示任何来源信息，包括 RAG 与
Web Search 的参考文档、内部文件名、文档标识、URL、页码和引用编号。完整来源只保留
在有权限的后台会话审计中。

## 2. 目标与非目标

### 2.1 目标

1. 在服务端统一保证所有聊天通道都不向微信消息追加 Web Search 来源。
2. Web Search 来源仍完整写入现有检索审计，后台审计页面保持可见。
3. 模型原生 Web Search 的最后一条用户消息只包含当前问题正文，避免
   `participant`、`content` 等格式标签污染搜索主题。
4. 对严格匹配的纯寒暄直接返回稳定问候，不调用模板 Agent、RAG、Embedding、
   Web Search 或模型自身知识。
5. 移除管理界面中已经失效的“在群消息中展示网页来源”开关，后端兼容旧请求，
   但始终把该值规范化为 `false`。

### 2.2 非目标

- 不删除或重建已有 Web Search 审计数据。
- 不修改知识库索引、Embedding、Qdrant 集合或 MySQL 表结构。
- 不改变 Web Search 是否启用、结果数、时间范围、域名过滤和摘要长度配置。
- 不对普通业务问题做大范围意图分类；本次只处理有限、明确的纯寒暄。
- 不依赖模型判断寒暄，避免为简单问候增加延迟和不确定性。

## 3. 方案选择

采用统一服务端策略，而不是只把私聊硬编码从 `true` 改成 `false`，也不在发送前
用文本规则删除“来源：”段落。

统一服务端策略能够覆盖私聊、群聊、Agent Framework 与兼容旧运行模式；审计来源
和用户可见文本在生成结果对象时就明确分离。发送前字符串删除容易误删正文中的
正常内容，也无法阻止其他调用路径重新拼接来源。

## 4. 详细设计

### 4.1 用户可见文本与审计来源分离

`GroundedAnswerService.NoEvidenceAsync` 在 Web Search 成功后：

- `AnswerDecision.GroupText` 始终使用净化后的模型回答正文；
- `RetrievalAuditDraft.WebSearchSources` 继续保存最多 20 个合法 HTTP/HTTPS 来源；
- 不再根据 `WebSearchShowSources` 调用 `AppendSources`；
- 删除仅用于聊天拼接的 `AppendSources` 实现。

该边界位于私聊与群聊共享的回答服务中，因此即使数据库存在历史
`WebSearchShowSources=true`，微信消息也不会再出现来源。

知识库回答继续使用带证据的 `Validate` 路径，并拒绝通用来源标记、命中的知识库
文件名、URI 和文档/版本/分段标识。RAG 提示继续明确禁止输出引用、来源标记、
文件名、内部标识和页码；传统聊天客户端与 Agent Framework 都只向模型提供已授权
证据正文，不额外提供来源元数据。

为避免模型偶发输出一个尾部来源段就导致整条业务答案变成澄清兜底，服务在严格验证
前先执行有界净化：仅删除从独立行 `来源：`、`参考文档：`、`Source:`、`Sources:`、
`Reference:` 或 `References:` 开始直到文本末尾的来源段，然后对剩余正文继续执行完整
输出防火墙。净化后为空，或正文其他位置仍包含文件名、URL、文档标识、页码、引用
编号、工具协议或系统提示标记时，仍按不安全输出处理，不能发送到私聊或群聊。

Web Search 与模型自身知识使用不带证据的 `ValidateUngrounded` 路径，继续拒绝来源
标题、引用编号、文档名、URL 和工具协议内容。Web Search 的结构化来源由
`ChatCompletionResponse.Sources` 单独写入审计，不进入聊天正文；被拒绝的输出继续走
现有降级路径，不能通过删除文本片段伪装成功。

### 4.2 兼容旧配置但禁止重新启用

暂时保留 `WebSearchShowSources` DTO、领域记录和数据库字段，避免破坏已有 API 客户端、
配置记录及迁移历史，但运行时语义固定为 `false`：

- 私聊默认回退配置改为 `false`；
- 群配置 API 读取时返回 `false`；
- 群配置 API 保存时忽略客户端传入的 `true` 并持久化 `false`；
- 管理前端移除“在群消息中展示网页来源”复选框；
- 前端草稿和 API 类型暂时保留字段并固定为 `false`，维持后端契约兼容。

本次不增加数据库迁移。历史 `true` 值不能绕过共享回答服务的强制隐藏，并会在以后
保存群配置时自然归一为 `false`。

### 4.3 GLM Web Search 问题消息

仅调整带 `WebSearchOptions` 的回退提示：

- 系统消息继续声明必须基于网页结果回答、安全返回纯文本；
- 会话摘要与历史消息继续放在明确的不可信数据块内；
- 当前问题作为最后一条独立 `user` 消息发送，内容为原始问题正文，不再添加
  `participant:`、`content:` 或问题块标签；
- 非 Web Search 的知识库回答和模型自身知识路径维持现有证据隔离格式，避免扩大
  安全边界变化。

该变更让原生搜索工具看到的最后一个用户查询就是 `你好` 或真实业务问题，而不是
格式元数据。系统提示仍负责约束用户输入不能覆盖内部规则。

### 4.4 纯寒暄短路

增加一个无外部依赖的共享寒暄判定器，对输入执行：

1. 去除首尾空白；
2. 统一英文大小写；
3. 去除末尾有限的中文或英文问候标点；
4. 仅在整体严格匹配白名单时命中。

初始白名单：`你好`、`您好`、`嗨`、`哈喽`、`hello`、`hi`、`在吗`。

命中后返回固定文本：`您好！请问有什么签证问题需要咨询？`。

以下内容不得被当成纯寒暄：`你好，日本签证需要什么材料`、`hi visa`、
`在吗，帮我查一下韩国签证`。它们继续走正常多轮、RAG 和回退链路。

调用位置：

- 群聊：通过入站策略与运行模式检查后，在模板路由和上下文/RAG 之前；
- 私聊：通过私聊命令识别后，在模板路由和上下文/RAG 之前。

群聊仍受现有是否需要回复、是否 @ 机器人和 IntentRuntimeMode 约束；寒暄短路不会
绕过群策略、安全停用或人工接管规则。

### 4.5 审计行为

纯寒暄仍要形成正常会话记录和发送命令，回答来源记录为稳定的
`conversational_greeting`，不伪装成知识库、固定模板、Web Search 或模型自身知识。
其 Web Search 来源数组为空。

普通 Web Search 回答继续记录：

- `AnswerSource=web_search`；
- 净化后的 `WebSearchSourcesJson`；
- Web Search 失败代码；
- 实际发送正文中不包含来源。

### 4.6 签证客服回答语气

私聊和群聊共用的知识库、Web Search 与模型知识回答提示统一要求模型以专业签证客服
身份直接服务客户：中文问题使用自然、礼貌、简洁的中文并称呼“您”；先回答已经能够
确认的内容，再根据业务需要主动询问签证类型、申请领区、职业、年龄或申请人类别等
缺失条件。

回答不得使用“系统中可查询到”“根据系统信息”等暴露内部实现的表达，也不得使用
“建议进一步咨询确认”这类把客户推向未知第三方的空泛话术。信息不足时应明确告诉
客户还需要提供什么，而不是声称稍后核对或让客户再次咨询。该约束只改变模型回答
风格，不改变证据阈值、来源隐藏、审计、固定回复模板或安全兜底策略。

## 5. 错误处理与安全

- 来源隐藏由共享回答服务强制执行，不信任前端或数据库开关。
- Web Search 仍要求非空回答、至少一个合法 HTTP/HTTPS 来源以及输出防火墙通过，
  才能判定为成功。
- RAG 与 Web Search 的来源均只进入审计，不进入私聊或群聊正文。
- RAG 尾部来源段只做有界删除；删除后的正文必须重新通过完整输出防火墙。
- 后台审计继续执行现有 URL 净化、权限校验和敏感数据脱敏。
- 寒暄匹配采用有限白名单，不调用 LLM，也不对包含额外业务文本的消息做猜测。
- 不更改回调鉴权、幂等、会话隔离、发送队列或 WorkTool 合约。

## 6. 测试与验收

### 6.1 后端单元测试

- `WebSearchShowSources=true` 时，用户可见回答也不包含 `来源：` 或 URL，但审计仍
  保存合法来源。
- Web Search 或模型自身知识直接生成来源标题、引用编号、文档名或 URL 时，输出防火墙
  拒绝该正文，来源不会进入微信消息。
- RAG 回答正文后附加 `来源：legacy-*.md` 时，来源段被删除，业务正文正常发送。
- RAG 回答只有来源段时，净化后为空并返回安全兜底。
- RAG 正文其他位置仍包含真实文件名、URL、页码、引用编号、内部文档标识、工具调用、
  函数调用、系统提示或不可信数据边界标记时仍拒绝。
- 知识库、Web Search 与模型知识提示都包含相同的专业签证客服语气约束。
- 中文问题的回答直接称呼客户，并在信息不足时询问明确的签证业务条件，不使用
  “系统中可查询到”或“建议进一步咨询确认”等系统化、推诿式话术。
- Web Search 最后一条用户消息严格等于当前问题正文，且不含 `participant:`。
- 知识库和模型自身知识提示结构保持原有行为。
- 寒暄白名单、大小写、空白和末尾标点命中。
- 带业务内容的问候不命中寒暄短路。

### 6.2 处理器与集成测试

- 私聊 `你好` 直接生成固定问候，不调用检索或 Web Search，并正常入发送队列。
- 群聊满足回复策略的 `你好` 同样短路；不满足群回复策略时仍不回复。
- 群配置提交 `webSearchShowSources=true` 后，读取结果和持久化值均为 `false`。
- 普通签证问题仍执行多轮改写、RAG 和现有回退链。

### 6.3 前端测试

- 群知识回答配置不再渲染“在群消息中展示网页来源”复选框。
- 其他 Web Search 配置仍可编辑保存。
- 运行 typecheck、Vitest 和生产构建。

### 6.4 完整验证

- 后端相关单元、契约和集成测试通过；
- `dotnet build WechatRobot.slnx -c Release --no-restore` 通过；
- 前端 `npm run typecheck`、`npm test -- --run`、`npm run build` 通过；
- `git diff --check` 通过；
- 使用本地配置进行一次受控私聊验证：`你好` 的回复语义正确且不含来源；
- 后台审计能看到 Web Search 来源，而对应微信发送正文不含来源。

## 7. 发布影响

需要重新发布 API、Worker 和管理前端：

- Worker 执行私聊、群聊、寒暄短路和回答生成；
- API 提供规范化后的群配置契约；
- 管理前端移除失效开关。

不需要 MySQL 迁移，不需要重建知识库索引，也不需要修改 Qdrant。
