# WorkTool 回调契约兼容修复设计

## 背景

WorkTool 在保存消息回调和指令结果回调前，会向目标 URL 发送测试
POST。当前公网回调 URL 可访问，但两个测试均收到 HTTP 400：

- 消息回调测试报文允许 `atMe` 使用字符串 `"true"`，当前 DTO 仅接受
  JSON 布尔值。
- 指令结果报文的 `type` 是实际指令类型，例如 `203`；当前 DTO 错把
  回调注册类型 `1` 当成结果报文类型。

## 方案选择

### 采用：字段级兼容和明确指令白名单

- 为 `WorkToolCallbackDto.AtMe` 添加专用 JSON 转换器，只接受：
  `true`、`false`、`"true"`、`"false"` 和 `null`。
- `WorkToolCommandResultDto.Type` 只接受当前系统实际发送的 WorkTool
  指令：`203`（发送消息）、`206`（创建群）、`207`（修改群）。
- 保留 token 验证、字段长度、群文本范围、结果列表大小和脱敏审计。

该方案范围最小，不会放宽整个 ASP.NET Core JSON 输入规则。

### 不采用：全局宽松 JSON

全局允许字符串转换为布尔值或数字会影响所有管理 API，扩大意外输入和
安全边界。

### 不采用：所有正整数指令类型均有效

系统只需要处理自己下发的指令。接受未知类型会让未实现的 WorkTool
能力进入结果处理链路。

## 数据流

### 消息回调

1. WorkTool POST 官方消息回调报文。
2. 专用转换器规范化 `atMe`。
3. 端点验证回调 token 和支持的群文本范围。
4. 合法消息进入原有持久化与 Durable Job 流程。
5. 返回 JSON `{"code":0,"message":"accepted"}`。

WorkTool 的配置测试报文与正式报文没有可靠的文档化区分标记，因此系统
不能基于猜测跳过它。若测试报文满足正式契约，它会按普通消息处理并由
现有去重规则约束。

### 指令结果回调

1. WorkTool POST 结果报文，其中 `type` 为 `203`、`206` 或 `207`。
2. 端点验证 token、字段范围和指令白名单。
3. 已知 messageId 更新对应发送命令或群操作。
4. 测试或未知 messageId 进入现有脱敏 orphan 审计。
5. 返回 HTTP 200 JSON 确认。

## 测试

- 合约测试：官方 `"atMe":"true"` 示例可以反序列化；其他字符串被拒绝。
- DTO 测试：`203/206/207` 有效，注册类型 `1` 和未知类型无效。
- 集成测试：官方消息示例返回 200；发送消息和群操作结果按实际类型完成
  对账。
- 回归测试：错误 token、超长字段、非群文本和未知指令类型仍被拒绝。

## 发布要求

修复本地验证通过后必须重新发布公网 API。WorkTool 校验访问的是
`https://wxrobot.aavisa.com`，仅重启本地 API 不会改变公网结果。
